# 02 · UX and screens

Mockups: [`docs/mockups/index.html`](../mockups/index.html) (each screen has a `#hash` id, listed below).

## Design language

- **Layout: docs-first.** The document is the center of gravity. The assistant, comments, changes and history live in a docked right panel.
- **Visual style: ChatGPT Codex app.** Calm monochrome surfaces, dense left sidebar with muted section labels, soft 1px borders, composer-style inputs (rounded box, toolbar row under the text, round send button). Color only carries state: revision status, presence, diff, warnings.
- **Components: shadcn/ui (New York).** Tailwind v4, shadcn CSS variables, lucide icons, Geist + Geist Mono. Radix primitives via shadcn: Dialog, Sheet, DropdownMenu, Command, Tooltip, Popover, Tabs, Resizable, Sonner.
- **Type scale.** UI 13px (sidebar, panels), 14px default, doc body 16px/1.7 with a ~720px measure. Tabular numbers for counts.
- **Themes.** Light and dark, follows system, manual override in profile.
- **Vocabulary.** Non-technical surfaces say Revision, Published, Submit for review, Publish, Version. Git terms (commit, branch, PR, SHA) appear only in technical detail areas: publish dialog, history details, repo settings.
- **i18n.** Every string goes through the i18n layer (`i18next` with ICU messages). English only in v1. Logical CSS properties so RTL works later.

## App shell

```
┌──────────────────┬────────────────────────────────────────┬──────────────┐
│ Sidebar          │ Top bar: breadcrumb · status · presence│ Right panel  │
│                  │   · Follow · Share · primary action    │ (toggle ⌘.)  │
│ Repo ▾           ├────────────────────────────────────────┤ Assistant    │
│ Published ▾      │ Editor bar: WYSIWYG/Source · Suggesting│ Comments     │
│  (revision picker)│   · Result/Changes (in review)        │ Changes      │
│ + New revision   ├────────────────────────────────────────┤ History      │
│ …context-specific│         Document (720px measure)       │ Links        │
│   sections…      │                                        │              │
│ ───────────────  │                                        │              │
│ You ▾            │                                        │              │
└──────────────────┴────────────────────────────────────────┴──────────────┘
```

- **Sidebar**: repo switcher, then the **revision picker**, then sections that depend on the context (see [Contextual sidebar](#contextual-sidebar)). User menu at the bottom (profile, theme, admin console, sign out). Collapsible (⌘\\). On mobile it becomes a Sheet.
- **Top bar**: breadcrumb (repo / folder / file), a compact status pill when in a revision, presence avatar stack, **Follow** (bell, for pages on Published), Share (invite collaborators to the revision), primary action by state and role (Submit for review / Resubmit for review / Approve 1 of 2 / Publish). In a revision's editor, **Save all** commits the revision to its branch (one commit per click, see [05](05-collaboration.md#saving-and-checkpoints)); it shows "Unsaved changes" when the content differs from the last commit and "All changes saved" otherwise. The live-sync indicator next to it reads "Synced", so it isn't mistaken for saving. A link opens the revision's pull request on the forge.
- **Editor bar**: WYSIWYG/Source toggle, Suggesting toggle, formatting. In review it adds the **Result | Changes | Source diff** switch.
- **Right panel** (resizable, collapsible to zero, ⌘.): tabs **Assistant**, **Comments**, **Changes**, **History**, **Links**. With the panel closed, comment threads show as margin bubbles beside the text.
- **Command palette (⌘K)**: search docs and headings, jump to revisions, actions (New revision, Ask assistant, Toggle source, Open history, Open graph), recent items.

## Contextual sidebar

The **revision picker** (top of the sidebar, under the repo switcher) decides where edits go and what the sidebar shows. It reads `Published ▾` or `Revision: <title> ▾` with a status dot, and opens a menu: Published, your open revisions and the ones you review (with state dots), New revision.

**Published context** (no revision selected):

- Home, Search (⌘K), Assistant, Graph, Inbox (unread count), Consistency (maintainers, with open findings count)
- Revisions: yours and "Review requested", grouped by state, "View all"
- Files: tree of the content root

**Revision context** (a revision selected):

- Status pill, reviewers' approval state ("Approved 1 of 2"), link to the revision overview
- **Changed in this revision**: files with M/A/D/R marks and +/− counts. This is how reviewers move between files
- **People**: editors and assigned reviewers, with presence dots
- **Checkpoints** link (the revision's commits)
- **All files** (collapsed tree; opening an untouched file shows Published content, the first edit adds it to the revision)
- Banners pinned at the top when relevant: "Updates from Published · Review and apply", "2 conflicts to resolve"

Behavior:

- In Published, the first keystroke by someone who can create revisions silently creates a revision named "Edits to <page title>", switches the picker to it and applies the keystroke there. Toast: "Started revision Edits to First week · Rename".
- People who can't edit the selected revision in its current state see it read-only with the reason ("In review with Maya and Sam. You can comment.", or "Request to edit").
- Switching never loses work. The last active revision per repo is remembered.
- Viewers typing in Published see: "You can view and comment. Ask a maintainer for edit access."

## Key flows

### F1 · Non-technical fix (Tom)

1. Tom opens `docs/onboarding/it-setup.md` from search. The picker shows Published.
2. He types. Revision "Edits to IT setup" is created. Toast offers Rename; he renames to "New laptop policy".
3. He drags in a photo. It uploads to `docs/onboarding/images/laptop-dock.webp` inside the revision.
4. He asks the assistant (right panel) "add a checklist for the first day". The assistant adds suggestions; Tom accepts two, rejects one.
5. He clicks **Submit for review**. A dialog shows the summary (auto-written by the assistant, editable), consistency findings ("Contradicts laptop-policy.md: refresh every four years"), and suggested reviewers (Maya, Sam). The revision becomes In review; Tom and Priya are now read-only and can comment.

### F2 · Live co-editing (Priya joins)

1. Tom clicks Share → invites Priya as a collaborator on the revision.
2. Priya opens the link, switches to Source mode, fixes a code block. Tom sees her cursor and the change live in WYSIWYG.

### F3 · Review and publish (Maya and Sam)

1. Maya and Sam get an inbox item (and a browser push) "Review requested: New laptop policy".
2. Maya opens it: the normal editor, in **Result** view, with changed passages marked in the gutter. She moves between files from **Changed in this revision** in the sidebar. The review assistant card lists a broken link and one contradiction.
3. She fixes a typo directly (her edit is live for everyone, credited to her), switches to **Changes** to double-check a deletion, comments on a sentence, and **Approves** (1 of 2).
4. Sam edits a table. Maya's approval resets ("Sam changed it-setup.md after your approval"). Maya re-approves; Sam approves. Approved.
5. Maya clicks **Publish**. Dialog shows the commit message and trailers. Published. Everyone involved gets an inbox item; followers of the pages too.

Alternative: Sam clicks **Request changes** with a note. The revision goes back to Editing, Tom and Priya can edit again, and resubmitting re-requests Maya and Sam.

### F4 · Updates from Published

1. Priya pushes directly to `main` from her laptop, touching `it-setup.md`, while the revision is In review.
2. kmdn prepares the update. Banner in the revision: "Published changed 1 page in this revision · Review and apply". Approve and Publish are blocked.
3. Maya (reviewer) opens the preview: 2 incoming changes, 1 conflicts with the revision's edits. She applies. Approvals reset, and because of the conflict the revision goes back to **Editing**. Tom and Priya are notified.
4. Tom and Priya resolve the conflict block in the editor (Tom picks "Keep this revision", Priya agrees in the conflict's thread), then Tom clicks **Resubmit for review**. Maya and Sam are re-requested.

### F5 · Feedback on published doc (Luis)

1. Luis highlights a sentence in the published remote-work policy, comments "This is outdated since July".
2. Maya sees it, clicks **Fix this** → a revision "Fix: remote-work policy" is created with the assistant briefed on the comment.

### F6 · Protected branch publish

Target branch protected → Publish opens PR #482 from `kmdn/<revision-slug>`. Revision state **Publishing**, with a link to the PR. When the forge merges it, the webhook moves the revision to **Published**. If the PR is closed unmerged, the revision goes back to Approved with a notice.

## Empty, loading and error states

- Repo not connected / mirror cloning: progress with ETA based on repo size.
- Forge unreachable: banner "GitHub is unreachable. Editing continues; publishing and sync resume automatically."
- WebSocket lost: presence greys out, "Reconnecting…" pill; edits queue locally in memory for the session (no offline persistence) and sync on reconnect; after 60s disconnected, the editor becomes read-only with a warning.
- LLM not configured: assistant tab explains that an admin must add a provider.
- Permission denied: plain explanation of the role needed and who the repo admins are.

## Accessibility

WCAG 2.2 AA target. Full keyboard navigation (sidebar, tree, panels, editor toolbar, dialogs). Visible focus rings. ARIA live region announcing remote collaborator joins/leaves and new suggestions. Diff colors are never the only signal (insertions underlined, deletions struck through, +/− markers in source diff). Respect `prefers-reduced-motion`.

Checked in CI: axe (WCAG 2.0–2.2 A/AA rules) on the main screens in the end-to-end suite (`e2e/tests/a11y.spec.ts`), plus a keyboard pass (skip link to the content, command palette) and the live region. Theme tokens meet 4.5:1 for text on every surface in light mode (muted text, success, warning, destructive); avatar colors keep white initials at 4.5:1; close buttons are at least 24 px. The file tree is nested lists of disclosure buttons and links (Tab-reachable) rather than an ARIA tree.

## Mobile

Breakpoints: `<768px` phone, `768–1279` tablet, `≥1280` desktop. Phones: read, search, comment (bottom sheet), review diff (rendered), approve, request changes, inbox. Editing works on tablets. Phones do not offer editing in v1.

On phones the sidebar is a sheet from the left and the right panel a bottom sheet (closed by default, opened by a comment highlight or the panel button). Revision pages show the editor read-only with a Result / Changes switch under the top bar and the review actions (Submit, Request changes, Approve, Publish) in a bottom bar; editing controls (toolbar, Suggesting, source mode, Add page, page actions, New revision, Edit) are hidden.
